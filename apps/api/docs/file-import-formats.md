# Statement file formats

The files `src/app/modules/file-import/parsers/` reads, for the import described in `file-import.md`.

| Format                    | Reader                              | Notes                                                                           |
| ------------------------- | ------------------------------------ | ------------------------------------------------------------------------------- |
| CAMT.053 and camt.052     | `src/app/modules/file-import/parsers/camt053.ts`                     | Also zipped, several statements per archive. Booked entries only.               |
| MT940                     | `src/app/modules/file-import/parsers/mt940.ts`, `src/app/modules/file-import/parsers/mt940-information.ts` | UTF-8, else Windows-1252, or for a Central European account Windows-1250 or ISO-8859-2 (below). Payee from the published `:86:` layouts. |
| OFX and QFX               | `src/app/modules/file-import/parsers/ofx.ts`                         | SGML and XML, bank and card statements. `LEDGERBAL` is the closing balance; an altered amount can't be caught (below). |
| ABN AMRO TXT              | `src/app/modules/file-import/parsers/abn-amro-txt.ts`                |                                                                                 |
| Revolut CSV and Excel     | `src/app/modules/file-import/parsers/revolut.ts`                     | Names no account; one statement per currency. Every completed row must state a balance, and from the second completed row of a product and currency on, that balance must equal the previous one plus the row's amount less its fee, or the file is refused; pending and reverted rows state no balance (one that does is refused) and are left out. The file states no opening or closing balance, so rows cut off at its start or end, or moved out of the last part of a chain, can't be caught. Excel numbers are rounded to eight places from their written digits. |
| Bank CSV layouts          | `src/app/modules/file-import/parsers/csv-layout-reader.ts`, `src/app/modules/file-import/parsers/csv-layouts.ts` | The banks below. Layouts are data; every row must validate. |
| The user's saved layouts | the same reader                      | Learned by the mapper, tried after everything built in, for that user only.    |

What the standard readers take from the text, by general rule and never per bank:

- **MT940 `:86:`.** German `?nn` subfields (DK): name in `?32`/`?33`, account in `?31`, purpose in `?20` to `?29` and `?60` to `?63` (`SVWZ+` as the payment text, `EREF+` as the reference), posting text in `?00`; a full 27-character subfield runs on into the next without a space, and the description carries no subfield codes. SWIFT-style codes (`/CNTP/account/BIC/name/city/`, `/BENM//NAME/`, `/ORDP//NAME/`, `/REMI/`, `/EREF/`), written continuously, so wrapped lines join without a space; without a `NAME` code the payer's `/ORDP/name?city` names a credit's counterparty and the payee's `/BENM/name?account` a debit's (`?` stands for a line break), and a field may leave out the first code's slash. The description holds the values without their codes. Free text names the counterparty only when its first line leads with an IBAN, or by the Polish keywords: `OD:` or `Nadawca:` on a credit, `DLA:` or `Odbiorca:` on a debit, up to the next `;`. Any other free text names none and stays in the description, since banks' narrative takes any shape. Several `:86:` fields after one entry (mBank) are read as one: each detail from the first field that has it, the descriptions joined. ABN AMRO keeps its own reader (`src/app/modules/file-import/parsers/abn-amro.ts`).
- **MT940 encoding.** UTF-8 when the file decodes as such. Otherwise the first `:25:` IBAN's country decides: Poland, Czechia, Slovakia, Hungary, Slovenia, Croatia and Romania get Windows-1250 or ISO-8859-2, whichever reads more of the other bytes as letters; any other account Windows-1252, which latin-1 is part of.
- **MT940 header.** A statement ends at `-`, or `-}` closing a SWIFT message, so each message keeps its own header; statements with none of their own share the one above. The bank's BIC comes from the lines above `:20:`: the sender of a SWIFT output message (`{2:O940…}`), else the basic header's address (`{1:F01…}`), else a BIC line over a `940` line, as ABN AMRO writes it. Like CAMT's, it is kept without its branch. Any other header line gives none, since a bank's name can look like a BIC.
- **MT940 `:61:` and balances.** Spaces in place of the entry date, a space before the transaction type and a two-letter type padded with a space are read; an entry without an entry date is booked on its value date (ABN AMRO: on the statement's date). A value or balance date of the 29th to 31st in a shorter month (30/360 interest entries, such as 30 February or 31 November) is that month's last day. An account in `:25:` may follow a slash. A statement whose entries do not add up to its closing balance is refused, and so is a file whose `:64:` available balance does not read as a balance (a file cut inside it).
- **CAMT.** Amounts are `xs:decimal`, so `.21` reads as 0.21, and a `Dt` may end with a time zone (`2026-10-01+02:00`), which is dropped: the date is read as written. The remittance text is the unstructured lines, then structured text (`AddtlRmtInf`) and creditor references (`Ref` in `CdtrRefInf`: Belgian structured communication, RF, Swiss QR) as written. The ultimate creditor or debtor is the counterparty when no direct one is named, and is added to the description when it differs from the named one. A camt.052 report (`Rpt`) is read like a statement: pending entries are skipped, and balances come only from the opening and closing booked balances, never an interim one (`ITBD`).
- **OFX.** Up to five HTTP-style header lines a download kept above the OFX header (`Content-Type: application/x-ofx`) are skipped. A file that decodes as UTF-8 is read as UTF-8 whatever its `CHARSET` says; otherwise `CHARSET:1252` or `CHARSET:8859-1` reads it as Windows-1252. A `DTUSER` that is not a date is left empty, since only `DTPOSTED` books the transaction. OFX states no opening balance, so an altered amount still imports: the ledger balance is taken as stated, and nothing in the file can show that the rows no longer add up to it. CDATA is text. A `BANKTRANLIST` left without its end tag is closed by the statement's end tag; every other aggregate needs its own. A bank account without an IBAN is named by `BANKID`, `BRANCHID` and `ACCTID` together, since an account number is unique only at its bank (UK sort codes, French bank and branch codes); a card by its `ACCTID`.

In any layout, a counterparty cell holding a BIC, a space and an IBAN (as Triodos writes it) is read as that IBAN. An empty value or transaction date is none; the booking date is required. On a card export the settlement date is the booking date and the purchase date the transaction date. A layout can take the other party from payer and payee columns by direction (DKB, Oberbank, Intesa): the payer's on money in, the payee's on money out, since the account holder fills the other side. Text layouts read UTF-8, Windows-1252, Windows-1250 (Polish, Czech, Hungarian) and UTF-16LE after its byte order mark; the table finder picks Windows-1250 when that reading gives letters where Windows-1252 gives symbols. Lines whose every cell is empty are no lines. Dates may name the month (`05 Oct 2026`, `10 Feb 18`), end in a dot (`2026.10.05.`) or carry a UTC offset after the time. An amount may start with a spreadsheet's apostrophe. A layout can name a column that marks rows not booked yet (a status such as `vorgemerkt` or `Umsatz vorgemerkt`, or a date cell saying `offen`, `PENDING_WORDS` in `src/app/modules/file-import/parsers/csv-layout.ts`): those rows are skipped and counted, never imported as booked.

Not read: QIF, PDF, old binary `.xls` (ABN AMRO's Excel download is one; its CAMT.053 and TXT are read). The built-in CSV layouts rest on public descriptions and samples from 2013 to 2026 (`test/fixtures/file-import/SOURCES.md`); none has been checked against a current export.

Adding a bank's CSV export is a new entry in `src/app/modules/file-import/parsers/csv-layouts.ts` with a synthetic fixture read row by row in `test/fixtures/file-import/expected.json` and its row in `test/fixtures/file-import/SOURCES.md`, the bank's entry in `BANK_LIST`, and its real file in the corpus (`real-file-corpus.md`), not a new parser. Write a parser only for a file that cannot be described as columns.
