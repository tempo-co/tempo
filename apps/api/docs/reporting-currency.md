# Reporting currency

The one currency every combined total is in, and how amounts are converted into it.

- `accounts.baseCurrency` is the user's reporting currency: every `amountInBaseCurrency` and every combined total is in it. Only `ReportingCurrencyService` (`src/app/modules/banking/services/reporting-currency.service.ts`) sets it; reads and the conversion job never pick one.
- While every active account holds one currency, that one is used (`AUTOMATIC`) as soon as authorization, a sync, an import or a removal shows it, and a currency the user never chose follows it, also when removing a bank leaves one currency where they were being asked. Once accounts hold several and a sync or import has finished, the user is asked once (`SETUP_PENDING`), and an automatic currency stays until they answer. Without one, `GET /reporting-currency` suggests the currency of the most booked transactions of the last 90 days, leaving out own transfers and currency exchanges; a tie suggests nothing, and nothing is saved without the user. A chosen currency (`CONFIRMED`) never changes by itself.
- The choice is EUR or a currency the ECB still publishes a daily reference rate for (`REPORTING_CURRENCIES`, derived from the ECB table in `@tempo/contracts`, which a monthly workflow keeps current). When the current currency is not one of them, because the ECB stopped publishing it or it was stored before users could choose, `GET /reporting-currency` reports `currencyUnavailable` and asks the user again, suggesting another currency. Nothing is stored for this, so a currency the ECB resumes is fine again once the table says so. Totals stay in the old currency until the user answers, and choosing it again is refused.
- A foreign amount without a bank-reported amount in the reporting currency uses the ECB reference rate of its own day (Friday's for a weekend, the previous publication for an ECB holiday). Until that day's rate is published, the newest stored rate at most `FX_RATE_MAX_AGE_DAYS` older stands in, so the row counts in totals at once, and the conversion job (queued after every sync or import that commits, and every 15 minutes) fetches its day's rate like an unconverted row's, whatever its age or account, and converts it again once a newer rate of either currency on or before its day is stored (`baseAmountRateDate` keeps the older of the two rates it combined, so either one can still be corrected). A row with no rate in that window stays unconverted and counts as `excluded.missingBaseAmount`.
- A change clears every converted amount of the user and copies the ones already in the new currency, in one transaction. When rows are left to convert it bumps `baseCurrencyRevision`, and totals are ready again once a conversion pass finishes for that revision (`baseAmountsRevision`). Until then every money response carries `baseCurrency: null` (`totalsCurrency`). A pass that leaves rows without a rate still finishes the change; those rows count as `excluded.missingBaseAmount`.
- Every transaction that writes converted amounts (sync and import writes, the conversion job) takes `lockReportingCurrencyForAmountWrites` as its first statement, and a change takes the same lock exclusively, so neither can write in the other's currency. Taken after a transaction has locked transaction rows, it can deadlock with a change. The conversion job also skips a user whose currency or revision changed after it fetched rates.
- A change queues a conversion pass at once; the 15-minute run and the boot backfill pick up one that was lost. Passes are deduplicated by job id, and BullMQ silently ignores a job added under the id of a retained failed one, so queueing a pass removes a failed job with that id first. Conversion runs while bank sync or file import is enabled. Tests run neither and call the job themselves.
