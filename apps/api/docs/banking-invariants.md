# Banking invariants

Rules for `src/app/modules/banking/` that the code relies on but does not state in one place. Write rules: `docs/derived-data-writes.md`.

## Ownership

- Every read, callback, sync and mutation is user-scoped through `bank_transactions` → `bank_accounts` → `bank_connections."accountId"`. A bank connection is not the ownership boundary: one user can have several connections, and one connection several accounts.
- Derived state is per user. Own-transfer recognition and currency-exchange pairing take a per-user transaction advisory lock (`pg_advisory_xact_lock(hashtext('own-transfer:' || ownerId))`, `'currency-exchange:'`); categorization history hints only read the same user's rows. Money moving between two different Tempo users stays ordinary spending/income.
- Unauthorized callers get 404, never a lock-conflict signal: do the user-scoped precheck before taking any shared lock.

## Provider account identity (Enable Banking)

From `src/app/modules/banking/services/enable-banking.client.ts` `parseAccount()`:

- `uid` → `bank_accounts.providerAccountId`. Session-scoped: it rotates on every authorization and only identifies an account within its connection's current session.
- `identification_hash` → `identificationHash`. Stable across sessions for the same real account.
- Account upsert/dedup must try `(connection, providerAccountId)` first, then `(connection, identificationHash)`. Deduping by `providerAccountId` across sessions silently creates duplicate accounts.
- Treat `identificationHash` as an opaque fingerprint. Never reverse it into an account number or log it next to IBANs.

## Re-authorization merges into the existing connection

`startAuthorization` always inserts a pending row, so failure and cancel stay per attempt. `persistAuthorizedSession` then writes the new session, consent and accounts onto the user's existing AUTHORIZED/EXPIRED connection for the same provider + ASPSP and drops the pending row. Account upsert by hash rotates `providerAccountId` in place, keeping history.

- The authorization state records `replacesConnectionId`: an exact id must still exist and be eligible, otherwise the callback fails with `state_superseded`; `null` may pick the newest eligible connection under lock.
- Serialize first-time callbacks with the account/ASPSP scope lock before selecting a reusable connection, or two pending rows can each become an authorized connection.
- The connection list leaves out unfinished attempts (`UNFINISHED_AUTHORIZATION_STATUSES`).
- In tests the newest row may be CANCELLED: never look up "the" connection by `createdAt DESC`; filter by status.
- Do not dedupe accounts globally per user by hash. It forces account re-parenting, and sync's authoritative-account reconciliation would then mark a borrowed account inactive (its `providerAccountId` is not in its own connection's session).

## Connection removal and sync coordination

Provider callbacks, background sync, deletion and Redis authorization state overlap.

- Sync and connection removal share one per-connection Redis lease (`banking:sync:<connection-id>`, `src/app/modules/banking/services/banking-connection-lock.service.ts`). Removal fails with 409 while sync holds it.
- Account deletion takes no lease. A sync write that locked its connection first commits before the deletion removes it, and reports ownership lost if its run went before it reported; a later one finds its connection gone.
- Connection removal and account deletion first delete each connection's provider session (`DELETE /sessions/{id}`, which closes the bank consent where the bank supports it), then the rows. Removal does it under the lease, after the same refusals the transaction checks, so a refused removal revokes nothing. Revocation is best-effort (`src/app/modules/banking/services/banking-consent-revocation.service.ts`): all of one deletion's sessions run in parallel under a shared 10-second deadline; a 404 or a session-ended code counts as revoked; any other failure is logged by code and HTTP status only and the local deletion goes ahead. Account deletion's `BankingConsentRevocationModule` is a leaf module, so the account module does not import `BankingModule`.
- Sync re-reads the owned connection **after** acquiring the lease, or it continues with a stale entity. Every success, failure and status write is fenced by the run identity (`syncStatus = RUNNING` + `syncStartedAt`); a zero-row fenced update means ownership was lost: roll back.
- Database lock order, matching account deletion: owner account row, imported-files connection, pending authorization row(s), reusable connection, then children. History writes first take sync leases and the reporting-currency lock (`src/app/modules/banking/services/account-history-writer.service.ts`); a sync's write then locks its connection, by run ownership, before its accounts.
- Destructive removal of AUTHORIZED/EXPIRED connections requires the exact body `confirmation: "DELETE"` unless it keeps the accounts (`keepAccounts: true`). Pending/cancelled/failed connections with child data are protected separately (409).
- Keeping moves accounts and imports to the imported-files connection: rows, edits and `identificationHash` stay, each account records the connection's `bankIdentity` (`src/app/modules/banking/bank-identity.ts`), the bank's last balance becomes the stated one. Authorizing again takes them back by hash, else IBAN and currency.
- Authorization states live in Redis for 10 minutes (`banking:authorization:<state>`); the key's TTL is their only expiry. Each is indexed per account and per connection (`banking:authorization-index:account:<id>`, `…:connection:<id>`), and removal and account deletion delete through those indexes, never by scanning keys. Storing the provider's authorization id is one compare-and-set that keeps the TTL; a state the callback already consumed fails with `state_consumed`.
- Delete, then remove Redis authorization state for every invalidated connection after commit. Release the lease in `finally`; a cleanup or logging failure must not turn a committed deletion into a reported failure.
- FKs from `bank_accounts`, `bank_transactions`, `bank_account_balances` and `bank_sync_runs` cascade on delete. Expired consent or an inactive account keeps rows; only explicit DELETE erases them.

## Background and foreground sync

- Data reads return Tempo's saved database state and never call the provider. Opening the authenticated app in the foreground can separately initiate an online refresh mutation while cached data remains visible. Unattended background sync never sends PSU presence headers.
- Foreground refresh is a verified-user, session-only, CSRF-protected `POST /bank-connections/:connectionId/refresh`. Check ownership before acquiring the shared lease, then re-read under the lease. It synchronously returns a finished `BankSyncRun` (`@wisp/contracts`) with HTTP 200 (or HTTP 204 when skipped as a recent sync, below), including partial/failed provider runs; expected refusals use typed HTTP errors and existing consent/conflict messages.
- Foreground refresh shares the incremental fetch/import, lease and fencing path. It bypasses the ordinary automatic `nextSyncAt` gate, but not consent expiry or an active provider `RATE_LIMITED` cooldown. When the connection synchronized (a SUCCEEDED or PARTIAL run sets `lastSyncedAt`) less than `BANKING_FOREGROUND_REFRESH_MIN_INTERVAL_MS` (5 minutes) ago, it answers HTTP 204 without contacting the provider or recording a run: opening Tempo repeatedly cannot fetch a bank more often than that. A cooldown refusal is HTTP 429 with `Retry-After`, `rateLimitSource` and `retryAfterSeconds`; a newly rate-limited run returns those metadata fields in the finished run.
- PSU context exists only within that request, from Express `req.ip` and the request User-Agent. Never use body-supplied PSU fields, incoming `Psu-*` headers, raw forwarding headers or server/public-IP discovery. Check the matching institution's catalog `required_psu_headers` (cached per country in Redis for an hour, `banking:aspsp-catalog:<country>`) before making presence-bearing requests; refuse missing/unsupported required context rather than sending an incomplete header set. Send the context to session/balance reads and every transaction page, including continuation after an empty page.
- Disconnect/abort cancels provider I/O, stops lease renewal and prevents subsequent page dispatch. Cancellation during provider fetch finishes the run as failed and restores its prior automatic schedule; never queue or replay foreground presence. PSU metadata is not persisted in banking rows or jobs. Cancellation racing with persistence may arrive too late to undo imported data.
- The existing trusted-proxy chain determines `req.ip`; a genuine private address (a VPN or local network) is not replaced or rejected merely for lacking public routability. Bank acceptance of such addresses is unproven and requires a separately approved live trial. See [Enable Banking's reference](https://enablebanking.com/docs/api/reference/) for PSU header and `required_psu_headers` semantics.
- A recurring dispatcher (`BANKING_SYNC_DISPATCH_INTERVAL`) enqueues due AUTHORIZED connections; the per-connection gate is `nextSyncAt` (`BANKING_SYNC_INTERVAL`). It skips a connection whose job is still waiting or running, writes QUEUED with a guarded update before adding the job (a job add that fails leaves the row due for the next dispatch), and one connection's error does not stop the others.
- A failed provider call is classified by `classifyProviderFailure` (`src/app/modules/banking/bank-sync-failure.ts`) from Enable Banking's documented error codes, never from substrings or a bare HTTP 403:
    - Session ended (`CLOSED_SESSION`, `EXPIRED_SESSION`, `REVOKED_SESSION`, `SESSION_DOES_NOT_EXIST`, or a session the provider reports in another status than AUTHORIZED): the connection becomes EXPIRED with no next sync, and only re-authorization helps.
    - Rate limit (HTTP 429 with any code, or `ASPSP_RATE_LIMIT_EXCEEDED`): stops the remaining provider calls in that run. The cooldown is `Retry-After` clamped to 15 minutes–24 hours (`BANKING_MIN_RETRY_AFTER_SECONDS`, `BANKING_MAX_RETRY_AFTER_SECONDS`), or 6 hours without a usable one; it becomes `nextSyncAt` with sync status RATE_LIMITED. Do not retry in a tight loop.
    - Tempo's own application refused (HTTP 401 without a session code, `UNAUTHORIZED_ACCESS`, `AUTHORIZATION_NOT_PROVIDED`, `UNAUTHORIZED_IP`, or Tempo failing to sign its JWT): stops the run, which fails with the ordinary retry backoff, and logs at ERROR because every connection fails until the key, application or clock is fixed. The connection stays AUTHORIZED.
    - Anything else, including a per-account HTTP 403 such as `ASPSP_ACCOUNT_NOT_ACCESSIBLE`: fails that call only; the run goes on with the other calls and ends PARTIAL or FAILED.
- The sync claim needs only the lease plus an AUTHORIZED connection with the session it read: a RUNNING row left by a crashed process is taken over, the new `syncStartedAt` fences out the old process's writes, and the connection's leftover RUNNING runs become FAILED with an `interrupted` failure. A fenced write that matches no row throws `BankingSyncOwnershipLostError` (HTTP 409) and the run's transaction rolls back.
- Fetch windows are per account. `bank_accounts.transactionsFetchedThrough` is the date (Europe/Amsterdam, `@core/time/app-time-zone`) of the account's last complete transactions fetch. Until one completes, the account asks for `strategy: 'longest'`; afterwards `strategy: 'default'` from that date minus `INCREMENTAL_OVERLAP_DAYS`, or from the earliest date of its oldest pending row when that is earlier, without `date_to`, relying on dedupe. When that start is older than `BANKING_UNATTENDED_HISTORY_DAYS` (90: many banks serve no more without the user present, and none publishes its limit), it asks for `longest` from that start instead, which returns what the bank still has rather than `WRONG_TRANSACTIONS_PERIOD`.
- Coverage is per account too: `syncCoveredFrom` and `syncCoveredThrough` on `bank_accounts` are the one range of days (app time zone, both included) that complete transaction fetches covered without a gap (`src/app/modules/banking/sync-coverage.ts`). Only a complete fetch (every page fetched, every row readable) moves it; one that dropped unreadable rows advances `transactionsFetchedThrough` but not coverage. A `default` fetch covers from its `dateFrom`; a `longest` fetch from the later of its `dateFrom` and the day after its earliest row (booking, else value, else transaction date), or only its own day when it returned none. The range ends at the fetch's date. A fetch starting no later than the day after the range extends it (or moves its start back); one starting later restarts the range. Coverage is null until the first complete fetch. Only providers in `SYNC_COVERAGE_PROVIDERS` record it (Enable Banking); add another only once its fetch time, re-read window and partial syncs are known.
- Bank sync is final for the days no later fetch reads again (`finalSyncDays`): the coverage without its first and last `SYNC_FINAL_MARGIN_DAYS` (`INCREMENTAL_OVERLAP_DAYS` + 1 = 8, since a file may date a payment by its purchase day), and never on or after the account's oldest pending row. Imported-files accounts and accounts without coverage have no final days. Accepted gap: the oldest day of a fetch that dropped an unreadable row can become final; its file row is then listed as never sent, for the user to add.
- Drain every continuation key, including pages with no rows. A key the provider already sent fails the call with `provider_pagination_loop`. When a later page fails, the pages before it are still imported, but the account's watermark only advances when every page was fetched.
- Banks allow few unattended calls per account per day, so a failed run is retried narrowly. A provider call that failed on its own (classified `failed`) is stored in `bank_connections.syncRetryCalls`, and the next automatic run, after the `BANKING_TRANSIENT_RETRY_BASE_MS` backoff, repeats only those calls (the session read, or one account's balances or transactions). If a call fails again in that retry, or nothing a retry can fix failed (unreadable rows only), the next sync is an ordinary full one after `BANKING_SYNC_INTERVAL`. Tempo's own credential refusals, unexpected exceptions and persistence failures retry the full sync with the exponential backoff. Foreground refreshes are always full.
- Keep provider calls outside database transactions; enqueue categorization only after the rows commit.
- Once the sync transaction commits, the run is finished: a later lease loss or disconnect does not fail it. Before it commits, fencing and the history writer's lease check protect the write.
- Every failed or partial run stores why in `bank_sync_runs.failures` (`src/app/modules/banking/bank-sync-failure.ts`) and logs the same summary at WARN with the run id: per failed provider call its kind (`session`, `balances`, `transactions`), Tempo's bank account id, the provider error code, HTTP status and whether `Retry-After` came back; `internal` for an unexpected exception (logged with its name and stack frames); `cancelled` for an aborted foreground refresh; `interrupted` for a run a crashed process left RUNNING. Never store or log provider messages, response bodies, provider ids or exception messages. The user-facing `errorMessage` stays generic.
- Transactions the provider sends without a usable amount, currency or direction (which the database requires) are not imported. The rest of the page is, the count is recorded as an `unparseable_transactions` failure for that account, and the run is PARTIAL. A page with no usable row fails that account's transactions call.

## Transaction identity

- Rows are unique on `(bankAccountId, stableIdentityKey)`, and every row has both `stableIdentityKey` and `stableIdentityGroupKey` (NOT NULL). The key comes from `src/app/modules/banking/bank-transaction-identity.ts`: a core group (dates, amount, currency, direction) plus an occurrence number. Descriptions, counterparty and references only disambiguate occurrences inside a group, compared trimmed, with whitespace collapsed and case folded. The group hash uses the stored values as they are, so changing its normalization changes every stored key.
- Inside a group, a new row first takes the stored row with the same details. When the same number of stored and new rows is left over, the provider edited them: they are paired, most equal details first, in a stable order. A booked row is never paired with a pending one, and a differing entry reference blocks a pair only when the fetch still sends the stored reference. Unequal leftovers get new occurrences.
- Provider transaction ids and entry references are hints, scoped to their account, never globally unique.
- A row keeps its key when it moves to another group, so a group's occurrence keys can be held by rows of other groups. Before allocating, look up the keys themselves (`findOccupiedTransactionIdentityKeys`: each incoming group's occurrences from 1 until there are as many free ones as incoming rows), never just the stored rows of the group, or an upsert can overwrite a different payment.
- Migrations compute identity keys with the frozen copy in `src/app/core/database/migration-support/bank-transaction-identity-v2.ts`, never with the live `src/app/modules/banking/bank-transaction-identity.ts`.
- The client fills a missing `booking_date` or `value_date` from `transaction_date` and says so; the row stores it in `bookingDateFilled` / `valueDateFilled`. A booked row continues a stored pending row across groups when it is the only candidate either way with the same transaction date, amount, direction, entry reference and details, and every date the provider sent for the pending row is unchanged; filled-in dates are ignored. Never merge amount/date look-alikes beyond that; genuinely repeated payments must survive.
- Pending rows are temporary. After a complete transactions fetch, `removeUnreturnedPendingTransactions` deletes the account's `PDNG` rows within the fetched window (all of their dates on or after its start; undated rows count as inside) that the fetch did not return: a released hold, or a payment booked as another row, for example at a changed amount. A fetch that failed a page or dropped unreadable rows removes nothing. A `longest` request counts as covering its requested start even when the bank serves less history; a pending row older than that is stale anyway. Deleting needs no other cleanup: recurring payments never use pending rows, an own-transfer or exchange leg's counterpart reference is set to null and the counterpart is decided again by the recompute after the sync, and categorization claims skip missing rows. User edits on a removed pending row go with it.
- Bank sync never waits on the user: its rows are stored as the bank sends them, and every question concerns a row that came from a file. On final days history holds only what sync sent: a file import adds no row there that the duplicate ladder did not match, and after a complete fetch has recorded coverage the same sync transaction removes every imported row on a final day that sync did not take over (`src/app/modules/banking/sync-sweep.ts`), except rows the user kept (a `bank_import_doubtful_rows` resolution `new` points at them). A user's answer is final. Sync asks nothing about an imported row on a day inside its coverage, which becomes final at most 8 days later. Details: `file-import.md`.
- A booked sync row takes over an imported row that the duplicate ladder in `src/app/modules/banking/bank-transaction-matcher.ts` matches or pairs with it: the imported row receives the sync row's identity keys and bank fields, keeps its `id`, category and manual edits, and loses its `importId`. Pending sync rows never take over. An imported look-alike it cannot pair is asked about, never merged. Takeovers and a statement's look-alike groups on an account its own IBAN confirmed are the only places amount/date look-alikes merge.
- Only an imported-files account's balance follows its rows (`src/app/modules/banking/services/file-account-balance.service.ts`); `bank_account_balances` stays sync-only and no computed `balanceAfterAmount` is written, since the duplicate ladder compares it.
- Date hydration depends on PostgreSQL `DateStyle`: use `to_char(date, 'YYYY-MM-DD')` in migrations and trust the stored group key during reconciliation.

## Provider field normalization

- Normalize currency and debit/credit codes at the authorization/sync persistence boundary.
- The counterparty is the party the direction names: creditor for `DBIT`, debtor for `CRDT` (Enable Banking: the creditor receives the funds, the debtor sends them). Its name and locality come only from that party. If it is missing, store neither name nor location; the other party may be the account holder. Keep only city, region and a valid two-letter country.
- `description` is bank text: the PSU note, else the remittance, else the bank transaction code's description. It never falls back to the counterparty name; display and merchant identity read that field themselves.

## Totals and financial events

Defined in `src/app/modules/banking/services/bank-transaction-filters.ts`; read `SQL_SPENDING` / `SQL_INCOME` before claiming how a category affects totals.

- Spending is every counted debit plus `REFUND` credits; income is every other counted credit. `SQL_COUNTED_IN_TOTALS` decides which rows every total counts: not internal (own transfer `ownTransferEvidence` or exchange `financialEventType`, never by category), not left out by the owner (`leftOutOfTotals`, still listed and in balances) and not on a hidden account (`isHidden`, still listed). Pending rows count, except pending own transfers. A `TRANSFER_OUT` to a person is spending.
- Currency exchanges are a financial event, not a category: `financialEventType = CURRENCY_EXCHANGE`, category status `NOT_APPLICABLE`. The same rules hold at every bank and provider; nothing depends on the bank's name.
- An exchange needs two legs that answer each other (`src/app/modules/banking/currency-exchange/`): each carries a marker, they sit on two accounts of the same user and connection, on the same day (booking date, else transaction date), in opposite directions and in two currencies, and a debit that names the bought currency names the credit's. Imported-files legs also need one shared, non-null `bankIdentity`. A marker alone never makes an exchange, so a payment whose text reads like one (remittance text is the sender's) stays spending or income. A marker (`detectCurrencyExchangeMarker`) needs the leg in its account's currency and is one of: a description or bank code label (`bankTransactionDescription`) that is exactly `Exchange to <currency>` or `Exchanged to <currency>` (debit: another currency; credit: its own), a description, code label, proprietary code or sub-code that is exactly the word `exchange` (any case; banks such as Revolut send it as the code label or code), or the ISO 20022 foreign exchange spot code. Enable Banking sends only the family as `code` and the sub-family as `sub_code`, never the domain, so `SPOT` alone counts; a code that carries a domain must name `FORX`. Texts and codes count only as a whole value: never match "exchange" as a substring (remittance text such as `Exchange of keys`, or a code such as `CURRENCY_EXCHANGE`), exchange-rate data or amount/date alone: card payments carry FX data, and the instructed amount is the leg's own amount, not the other leg's. Two texts naming different currencies, or a named currency that contradicts the leg, are no marker. Unmarked same-day legs in two currencies are common and are not exchanges.
- The recompute after the sync decides the event; persistence only stores the provider fields and keeps every row's categorization input hash. A row the worker holds (`PROCESSING`) is still overwritten when it now carries a marker. A row that becomes an exchange has its category reset to `NOT_APPLICABLE` unless the category is manual; one that stops being an exchange goes back to `PENDING` and is enqueued after own transfers. Block event rows at every AI boundary (enqueue, reconciliation, worker claim, the claim renewal before each model call after the first): stale jobs bypass a single guard.
- Own transfers: evidence is a counterparty IBAN of another owned account in the same currency, the holder's own name (never for card payments), or the user's `MARKED` override (`UNMARKED` takes a row out). The name is the stored counterparty, else the description's SEPA `Naam:` field or `To <name>`/`Payment from <name>` wording, at any bank. Holder names compare across all the user's accounts, so a transfer to their account at an unconnected bank, or one whose IBAN no bank reports, is internal. Booked non-card legs without evidence, naming no other party, also pair when one bank group (`bankGroupOf`) reports both accounts, same day, same description (case and spacing aside). Type, names or amount/date alone are leads, not evidence. A pending row is an own transfer only on its own evidence, never as the unproven second leg, so it stays out of spending and income until it books. Never delete, merge or rewrite either leg.
- Never add amounts across currencies.
- The breakdown (`/bank-transactions/breakdown`) splits cash flow's spending by category and its income by source (`SQL_INCOME_SOURCE`: merchant key, else display name) on the same definitions, so each period's total equals cash flow's. Refund credits stay in their `REFUND` part, which can be negative. A source's part reconciles with the list filtered by `incomeSource` set to its key. Parts count rows; `allCategories` spans both directions.
- Merchant totals (`/merchants`, optionally of one `category`) reuse them over `SQL_MERCHANT_GROUP` and reconcile with the list so filtered; own transfers and currency exchanges belong to no group.
- The ledger (order, days, filter) and all totals use `date`: transaction, else booking, else value date. Periods come from `periodWindows`: which periods history covers, ends clamped to the range, and which are complete.

## Alerts

- `src/app/modules/banking/alerts/` raises bank alerts (consent ending within 7 days, its last day, no successful sync for `SYNC_BROKEN_AFTER_MS`) by email and push. "Successful" means a SUCCEEDED run: `lastSyncedAt` also advances for PARTIAL runs. `GET /bank-connections` returns that time as `lastSuccessfulSyncAt`, and the web app warns about a failing sync on the same threshold. Each alert is recorded once per episode (the connection's marker columns), in the transaction that queues its jobs. Job ids derive from that identity, so a rolled-back marker, a retry or an overlapping scan never sends twice.
- A push raised between 21:00 and 09:00 in the user's time zone (`accounts.timeZone`) waits until 09:00 there as a delayed job; the delay is fixed when the alert is queued. Alert emails write their times in that zone too. The zone is an IANA name the API's `Intl.supportedValuesOf('timeZone')` lists, or `UTC`, stored in the API's spelling: signup stores the browser's zone, or `APP_TIME_ZONE` (Europe/Amsterdam) when it is missing or unsupported, and Settings changes it (`PATCH /accounts/me` refuses an unsupported one). Before sending, the worker checks that the alert still applies (a reauthorized or synced bank sends nothing) and reads the badge count from review counts.
- Push text stays vague: no bank, account or amount. Pushes reach only subscriptions whose session is still signed in as the user (`src/app/modules/notifications/`); logout removes that session's subscriptions, and push service 404/410 answers remove the subscription.

## Concurrency patterns used here

- User answers that must not race (recurring-series decisions): lock the user's account row (`SELECT id FROM accounts WHERE id = $1 FOR UPDATE`) inside the write transaction, re-read the decision state and return 409 when it changed. Test with two simultaneous requests (`Promise.all`) asserting exactly one success and one stored row.
- After each committed sync, import, authorization, removal or amount conversion, the derived-data refresh (`src/app/modules/banking/services/derived-data-refresh.service.ts`: steps per change) runs, in order: reporting-currency reconcile (not after a conversion or failed sync write), exchange recompute, own-transfer recompute (skips exchange legs), then enqueues model-eligible written rows and former exchange legs for categorization, and for logos a sync's written rows or, after a file write with rows, the whole history. Steps tolerate earlier failures. Recomputes serialize per user on an advisory lock; one inside a writer's transaction takes it before touching rows, or recomputes deadlock.
- A sync's own-transfer recompute is scoped to its written rows, rows whose exchange classification changed and the former counterparts of the pending rows it removed (their evidence may have come only through it). It reads only rows sharing their currency and amount (legs pair on nothing else; `idx_bank_transactions_account_amount`); a sync that changed none of them does no own-transfer work. A conversion recomputes own transfers only when exchange classification changed (detection reads no converted amount). Everything else, a failed exchange recompute (after a conversion too) and a failed scoped one (retried at once) recompute the whole history. A new writer of a field detection reads (amount, currency, dates, status, type, exchange classification, counterparty IBAN, counterparty name, description, override, the user's accounts) recomputes the whole history after it. A daily run (03:00 UTC, `recompute-own-transfers`, amount-conversion queue) repeats exchanges, own transfers and categorization per user.
- Recurring detection is stored per user (`recurring_snapshots`) and reused while the user's history version is unchanged. Statement triggers on `bank_transactions` (migration `AddBankHistoryChanges20261113170000`) add a change note per user and writing transaction for every insert, delete and update of a tracked column; the version is the sum of the notes plus the user's bank account ids, which covers rows deleted with their account. Writers insert only their own note key, so they never wait for each other, and reads fold many notes into one of the same weight. The daily whole-history recompute then folds the notes of every user with more than one, so users who never read recurring payments keep few notes too; a fold keeps the version, so stored detections stay valid. Every column counts except the untracked list in that migration (categorization bookkeeping, pair links, rule versions, `updatedAt`); a column detection starts reading must not be on it. Detection reads no `bank_accounts` or `bank_connections` column besides the ownership join and `isHidden`, marked per account in the version; another such filter needs a note. `TRUNCATE` writes no note.
- For conflict upserts, inspect the generated SQL and run it against real PostgreSQL; qualify target-table columns in `ON CONFLICT ... WHERE`, or they become ambiguous with `EXCLUDED`.

Test conventions: `apps/api/AGENTS.md` and `docs/e2e-and-seeding.md`.
